Case study

CloudFlow: a serverless image-processing platform on AWS

A personal project by Adhwaith. I built it to learn how AWS services fit together in a real application.

Deployed 5 November 2026AWS us-east-2

Explore ArchitectureEngineering NotesView Evidence
01

The problem

Resizing a batch of images is slow, unpredictable work, and a normal web API is a poor fit for it. The caller holds a connection open while the server works, and Amazon API Gateway cuts any request off after 29 seconds.

  • Batch resize time: about a second to a couple of minutes
  • Failure mode of a synchronous API: a timeout with no job state
Technical details

A slow job also blocks everything behind it, and if processing fails halfway the caller has no idea what happened to the job. The better pattern is to accept the request quickly, do the work in the background, and let the caller check on it. That is easy to say and has a lot of detail in practice: where the work waits, what happens when it fails, how to stop the same job running twice, and how the caller gets the result back safely.

02

The idea

I was studying for the AWS Solutions Architect Associate exam. I could describe SQS and Lambda one at a time, but I had never connected them into something that worked end to end. So I took a published queue-and-worker pattern and built a real image resizer on it, with sign-in, direct uploads and downloads.

  • Everything defined in Terraform, so it can be created and destroyed repeatedly
  • Runs inside the AWS Free plan's credits, with a personal ceiling of $10 for the whole project
  • Every decision explainable, from the queue to each IAM policy
Technical details

The starting point was the "Asynchronous API Patterns with SQS" recipe by mzazon on CloudProjects.dev, which shows API Gateway writing to an SQS queue and a Lambda function processing the messages. I used the pattern, not its code.

What changed from the recipe: the open endpoints became authenticated and validated, the Lambda code moved out of Terraform into its own Python package with tests, and I added retries, duplicate protection, per-function IAM roles, alarms and lifecycle rules. I wanted to be able to explain why the queue is there, what each IAM policy allows, what happens to a failed message, and how I would know something broke.

03

The architecture

A signed-in user uploads images straight to S3, submits a job, and polls for the result while a worker on the other side of a queue does the resizing. The API and the worker never call each other.

Open the interactive architecture →

  • Upload: presigned POST forms send image bytes straight to a private S3 bucket, never through the API
  • Queue: POST /jobs records the job in DynamoDB and queues a small SQS message, never image data
  • Worker: a Lambda function claims the job with one conditional write and resizes the images with Pillow
  • Failure: a message that fails three times moves to a dead-letter queue, and a CloudWatch alarm publishes to SNS
Technical details
  • Sign-in: the Cognito hosted page, authorization code flow with PKCE; API Gateway checks the ID token on every request
  • Upload: POST /uploads returns the presigned POST forms for the private input bucket
  • Submit: the SQS message carries the job id, the owner and the S3 keys
  • Process: the worker reads the inputs from S3 and writes outputs and a manifest to the private results bucket
  • Status and download: GET /jobs/{jobId} returns the job's state and five-minute download links, only to the job's owner

The diagram is generated from the same data that a test checks against my Terraform configuration, so it cannot drift from what is deployed. IAM, X-Ray tracing, CloudWatch Logs, the AWS Budget with its cost guard, and Terraform are drawn as a separate strip: they control and observe the services, they are not part of the data flow. A corrupt image is handled differently from a broken message: it fails on its own, is recorded with a short reason, and is not retried, because retrying cannot fix a bad file.

04

Building CloudFlow

I started with the smallest version of the pattern: an API that accepts a job, a queue, a worker doing a trivial task, and a status endpoint. I deployed it, broke it on purpose, and destroyed it the same day. Only then did I add image processing, sign-in and uploads on top.

  • The API does not process anything. It validates, records and enqueues, so a spike in jobs fills the queue instead of overloading the API
  • Failures are sorted into kinds. A broken message is dead-lettered, bad input is recorded and never retried, a temporary AWS error is retried by the queue
  • Everything is tested without AWS first. moto emulates AWS in memory, so awkward failure cases are covered
Technical details

Uploads skip the API. Image bytes through API Gateway and Lambda would be slow and hit payload limits; a presigned POST lets the browser talk to S3 while my code still decides the exact key, type and size.

05

Security by design

Every layer refuses what it does not expect. Sign-up is limited to capped 24-hour test accounts that delete themselves, each function has its own narrow IAM role, and one user can never reach another user's files or jobs.

  • Authentication: Cognito sign-in with PKCE; self sign-up is limited to 24-hour test accounts with a cap on how many exist and daily quotas per account; the console's API routes require a valid Cognito ID token
  • Least privilege: one IAM role per function, limited to the exact actions and resources its code uses; a test fails the build if a policy is widened
  • Signed uploads: each presigned POST accepts one key, one content type and 1 byte to 5 MB, and expires after 60 seconds
  • User isolation: one account cannot read another account's job or use its uploads
Technical details
  • Private storage: both buckets block all public access, are encrypted, and accept TLS only
  • Input validation: JSON schemas at API Gateway, and the worker refuses images over 24 megapixels before decoding them
  • API protection: per-method throttling, daily quotas on jobs and upload requests, and request alarms that pause the service automatically

The worker checks an image's declared size before decoding it, because a file that is tiny on disk can claim to be tens of thousands of pixels wide, and it only accepts the three formats I intend to support. The owner of a job comes from the registered job record, never from the queue message.

06

Reliability and challenges

The hard parts were the ones I only found by deploying. Two came from reading logs, one from how SQS delivers messages, and one from a review of my own cost limits.

  • Every request returned 500. API Gateway could not assume its role: my trust policy required aws:SourceAccount, which API Gateway does not supply for a service integration
  • Download links returned 403. They were signed for the general S3 address, so the signature no longer matched once S3 redirected them
  • The same message can arrive twice. SQS delivers at least once, so one conditional write now checks and claims the job
  • My cost limits did not limit what I thought. One throttle was about nine times looser than I intended; I fixed it and added alarms that pause the service
Technical details
  • The 500s: aws:SourceAccount works for Lambda roles. I removed it from that one role and wrote the reason next to the policy
  • The 403s: I now create the S3 client for the bucket's region, and a test checks the link's host name
  • Duplicates: the conditional write replaced a check-then-write, and a lease lets another worker take over if one dies
  • Cost limits: the review found no quota on upload links, up to 21 S3 calls per read, and a throttle that applied per method. I fixed all three

A second copy of a message that finds a live lease is put back for later instead of being deleted, because deleting it could remove the only remaining copy. One corrupt image used to make the whole job retry three times and land in the dead-letter queue with nine good images; the worker now treats each file separately. The pause was tested on the real deployment: a steady stream of requests tripped the alarm after five and a half minutes, and the service paused itself one second later.

07

The results

On 5 November 2026 one terraform apply created 120 resources in us-east-2, and I verified the running service through the public page the same day. On 7 November I signed in with my own account and processed a real image end to end.

  • Speed: three images resized and downloadable 4.2 seconds after the click; ten images in 6.7 seconds
  • Safeguards: the 11th job and the 21st upload request of the day refused; a broken message dead-lettered and raised the alarm
  • Errors: zero Lambda errors and zero 5xx responses across the run
  • Cost: about one cent of credit for the deployment, every test and both drills
Technical details
  • Deployed: 120 resources, one apply, nothing refused by the Free plan account
  • My own job: completed on the first attempt in 648 ms of worker time, output 640 × 263 JPEG as requested
  • More safeguards: an expired upload link refused by S3; a corrupt file failed alone while the rest of its job completed
  • Tests: 413 Python tests, 79 JavaScript tests, headless-browser checks, Terraform validation and a secret scan on every push

Three jobs submitted together all completed on the first attempt, with worker concurrency peaking at the cap of 2. Two duplicate copies of a finished job's message were skipped. Both safety drills worked: a test alert paused the service within about a second, and a request flood tripped the alarm and paused it automatically. The first deployment, on 4 November 2026, was the queue-and-worker core alone: 51 resources created, 59 jobs completed, a dead-letter drill, two real bugs found and fixed from logs, and all 51 resources destroyed afterwards with nothing left behind.

08

What I learned

  • Serverless and event-driven design. The queue is what makes the system tolerant. The API and the worker never call each other, so either can slow down or fail without taking the other with it, and a failed job has somewhere to wait for a retry.
  • IAM. A trust policy and a permissions policy answer two different questions: who may use this role, and what may it do. My first deployment bug was in the first one. Writing permissions for exact actions on exact resources took longer than broad ones, and it is the part I would least want to skip.
  • Security. Most of the security here is about refusing early: validating requests at the API, pinning each upload to one key and size, checking ownership on every read, and keeping details out of error messages and logs.
  • Infrastructure as code. Because everything is in Terraform, I could destroy the whole environment and bring it back with one command, and the plan output became the thing I review before any change.
  • Monitoring and troubleshooting. Both real bugs were found by reading logs. An alarm or a safety switch that has never fired is untested, so I triggered each one on purpose on the real deployment.
  • Cost. Almost everything here costs nothing while idle, but a limit is only real once I know exactly what it counts.
Technical details

What I would improve: push updates over a WebSocket API instead of polling; a per-user monthly quota and safe self-service sign-up; a deployment pipeline with a manual approval step (it needs AWS credentials in CI, which I chose not to do for a personal account); multipart uploads for files over 5 MB; and S3 with CloudFront instead of GitHub Pages if keeping everything on AWS ever matters more than simplicity.

            Two problems I found and fixed
            
          
            
            
            
              
            Bug 1Every submit returned 500
            
              
            
                
            Symptom
            Valid requests passed validation, then 500 Internal server error. Nothing reached the queue.
            
                
            Cause
            The API's IAM role trust policy carried an aws:SourceAccount condition. API Gateway does not populate that key when it assumes an integration role, so the assume-role call was refused. Found in the execution log.
            
                
            Fix
            Removed the condition from that one role; the Lambda roles keep it. Redeployed within the hour.
            
              
            
              Evidence 03 →
            
            
            
            
              
            Bug 2Download link answered 403
            
              
            
                
            Symptom
            Status said completed with a signed link, but fetching it gave 403 Forbidden after a redirect.
            
                
            Cause
            The link was signed for the legacy global S3 host. S3 redirected the us-east-2 bucket to its regional host; the signature covers the host, so it no longer matched.
            
                
            Fix
            Sign against the regional endpoint with SigV4; a regression test asserts the regional host. Verified: 200, zero redirects, byte-identical file, tampered signature refused.

            Security and reliability mechanisms
            
          
              
            
            • Cognito + PKCE. Sign-in on the hosted page with the authorization code flow; the browser never holds AWS credentials.
              • 
            
            • Presigned POST policy pins. Uploads are pinned to one key, one content type and a 1 byte to 5 MB size range, and the upload form expires after 60 seconds.
              • 
            
            • Per-user prefixes. Each user's inputs and results live under their own id; one user cannot list or read another's.
              • 
            
            • IAM per function, with a static test. Every Lambda has its own role scoped to exact actions and resources, and a test fails on a wildcard or on a policy outside the reviewed set.
              • 
            
            • Atomic claim + lease. A conditional write gives a job to one worker; a lease that expires lets another worker take over a dead one.
              • 
            
            • Per-file failures are never retried. A corrupt image fails alone with a short reason; the other files still finish.
              • 
            
            • Alarms + dead-letter queue. Three failed receives park the message and raise a CloudWatch alarm.
              • 
            
            • No secrets in the repository. Keys come from the environment or SSM Parameter Store; the public build and the CI pipeline scan for secret-shaped text and refuse to publish it.
