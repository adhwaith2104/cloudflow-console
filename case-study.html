CloudFlow: a serverless image-processing platform on AWS

A personal project by Adhwaith. I built it to learn how AWS services fit together in a real application.

1. The problem

Resizing a batch of images can take anywhere from a second to a couple of minutes. A normal web API is a poor fit for that kind of work. The caller has to hold a connection open while the server does the processing, a slow job blocks everything behind it, and Amazon API Gateway cuts any request off after 29 seconds. If the processing fails halfway, the caller usually finds out with a timeout and no idea what happened to the job.

The better pattern is to accept the request quickly, do the work in the background, and let the caller check on it. That is easy to say and has a lot of detail in practice: where the work waits, what happens when it fails, how to stop the same job running twice, and how the caller gets the result back safely.

2. Why I built this

I was studying for the AWS Solutions Architect Associate exam and I could describe services like SQS and Lambda one at a time, but I had never connected them into something that worked from end to end. I wanted a project where a request comes in, real work happens in the background, and a real result comes back, with authentication, permissions, monitoring and failure handling that I had configured myself.

3. Where the idea came from

The starting point was the "Asynchronous API Patterns with SQS" recipe by mzazon on CloudProjects.dev, which shows API Gateway writing to an SQS queue and a Lambda function processing the messages. I did not copy its code. I used the pattern and then changed most of the details: the open endpoints became authenticated and validated, the Lambda code moved out of Terraform into its own Python package with tests, and I added retries, duplicate protection, per-function IAM roles, alarms and lifecycle rules. The recipe's example job was a placeholder, so I turned it into something useful: an image resizer with sign-in, direct uploads and downloads.

4. What I set out to do

Technically, I wanted an application where a signed-in user uploads images, chooses a size and format, submits a job, and downloads the results, with every step running on managed AWS services and nothing running on a server I have to keep alive.

For my own learning, I wanted to be able to explain each decision: why a queue sits between the API and the worker, what the IAM policy for each function allows and why, what happens to a message that fails, and how I would know if something broke.

I also set myself two rules. The whole thing had to be defined in Terraform so I could create and destroy it repeatedly, and it had to run inside the AWS Free plan's credits with a personal ceiling of $10 for the whole project.

5. What I built

CloudFlow is a small web application for resizing images.

  • You sign in through Amazon Cognito. Accounts are created by me; there is no public sign-up.
  • You choose up to ten JPEG, PNG or WebP files of up to 5 MB each, and the output size, format and fit.
  • The browser uploads each file straight to a private S3 bucket using a short-lived presigned upload that only accepts that file's name, type and size.
  • You submit the job. The API replies immediately with a job id.
  • A Lambda function picks the job up from a queue, resizes the images with the Pillow library, and writes the results to a second private bucket.
  • The page shows the job's status as it changes, then previews and download links that work for five minutes.

Visitors who are not signed in can still use the page: it resizes images in the browser and walks through a simulation of the AWS pipeline, clearly labelled as a simulation. That mode also takes over if the AWS backend is paused or the Free plan ends.

6. Architecture

The interactive diagram on the Architecture page is generated from the same data that a test checks against my Terraform configuration, so it cannot drift from what is deployed. The main paths:

  • Sign-in. The browser goes to the Cognito hosted sign-in page (authorization code flow with PKCE) and comes back with an ID token. API Gateway checks that token on every request.
  • Upload. POST /uploads returns presigned POST forms. The browser sends the image bytes directly to the private input bucket. The API never handles the bytes.
  • Submit. POST /jobs records the job in DynamoDB as queued and puts a small message on the SQS queue: the job id, the owner and the S3 keys. Image data never travels through the queue.
  • Process. The worker Lambda claims the job with a single conditional write to DynamoDB, reads the inputs from S3, resizes them, writes the outputs and a manifest, and records the outcome for each file.
  • Status and download. GET /jobs/{jobId} returns the job's state and presigned download links, only for the user who owns the job.
  • Failure. A message that fails three times moves to a dead-letter queue. A CloudWatch alarm on that queue publishes to an SNS topic. A corrupt image is different: it fails on its own, is recorded with a short reason, and is not retried, because retrying cannot fix a bad file.

IAM, X-Ray tracing, CloudWatch Logs, the AWS Budget with its cost guard, and Terraform are drawn as a separate strip. They control and observe the services; they are not part of the data flow.

8. How I built it

I started with the smallest version of the pattern: an API that accepts a job, a queue, a worker that does a trivial task, and a status endpoint. I deployed that, tested it, broke it on purpose, and destroyed it the same day. Only then did I add the image processing, sign-in and uploads on top.

A few decisions shaped the rest:

  • The API does not process anything. It validates, records and enqueues. That keeps every request fast and means a spike in jobs fills the queue instead of overloading the API.
  • Uploads skip the API. Sending image bytes through API Gateway and Lambda would be slow and would hit payload limits. A presigned POST lets the browser talk to S3 directly while my code still decides exactly which key, type and size are allowed.
  • Each function gets its own role. The API function can create upload forms and enqueue jobs but cannot delete objects or scan the table. The worker can read uploads and write results and nothing else.
  • Failures are sorted into kinds. A broken message goes to the dead-letter queue. Bad input is recorded and never retried. A temporary AWS error is retried by the queue. Deciding which is which, per message, was most of the worker's logic.
  • Everything is tested without AWS first. The tests use moto to emulate AWS in memory, so I could check failure cases that are awkward to produce on the real services.

I used an AI coding assistant throughout this project, for writing and reviewing code, tests and Terraform. I directed the work, made the design decisions, ran the deployments in my own account, read the logs when things failed, and I can explain how each part works. I am noting this because it is how the project was actually built.

9. Challenges

Every request returned 500. After my first deployment, every job submission failed. The API Gateway execution log said it did not have permission to assume the role I had given it. I had added a condition to that role's trust policy (aws:SourceAccount) because it is good practice against the confused-deputy problem, and it works for Lambda roles. It turns out API Gateway does not supply that value when it assumes a role for a service integration, so the condition could never be satisfied. I removed it from that one role, kept it on the Lambda roles, and wrote the reason next to the policy so nobody adds it back.

Download links returned 403. Jobs were completing but the download links were rejected. The links were being signed for the general S3 address rather than my bucket's regional address. S3 redirected the request, and because the signature includes the host name, the redirected request no longer matched. I fixed it by creating the S3 client for the bucket's region explicitly, and added a test that checks the host name in the generated link.

The same message can arrive twice. SQS standard queues deliver at least once, so two copies of one job can be processed at the same moment. My first version checked the job's status and then wrote, which leaves a gap between the check and the write. I replaced it with a single conditional write that both checks and claims the job, and added a lease so that if a worker dies, another one can take over after a timeout. A second copy that finds a live lease is put back for later instead of being deleted, because deleting it could remove the only remaining copy.

One bad image should not fail the batch. At first a corrupt file made the whole job retry three times and then land in the dead-letter queue, along with the nine good images. I changed the worker to treat each file separately: a bad file is recorded with a short reason, the others finish, and nothing is retried unless the failure was on the AWS side.

Images that are small on disk and huge in memory. A tiny file can claim to be tens of thousands of pixels wide. The worker checks the declared size before decoding, refuses anything over 24 megapixels, and only accepts the three formats I intend to support.

My cost limits did not limit what I thought they did. Before deploying the service to stay up, I had the cost controls reviewed, and the review found three gaps. I had a daily quota on jobs, but none on requests for upload links. Reading one job made up to 21 calls to S3. And the throttle I had set to 10 requests a second turned out to apply to each API method separately, so the real limit was about nine times higher, including on the CORS preflight requests that anyone can send without signing in. I added a quota on upload requests, made upload links expire after 60 seconds, removed the S3 calls from reads, set a limit per method, and added alarms on the request count that pause the service automatically. Then I tested the pause on the real deployment: a steady stream of requests tripped the alarm after five and a half minutes, and the service paused itself one second later.

10. What I learned

  • Serverless and event-driven design. The queue is what makes the system tolerant. The API and the worker never call each other, so either can slow down or fail without taking the other with it, and a failed job has somewhere to wait for a retry.
  • IAM. A trust policy and a permissions policy answer two different questions: who may use this role, and what may it do. My first deployment bug was in the first one. Writing permissions for exact actions on exact resources took longer than broad ones, and it is the part I would least want to skip.
  • Security. Most of the security here is about refusing early: validating requests at the API, pinning each upload to one key and size, checking ownership on every read, and keeping details out of error messages and logs.
  • Infrastructure as code. Because everything is in Terraform, I could destroy the whole environment and bring it back with one command, and the plan output became the thing I review before any change.
  • Monitoring and troubleshooting. Both real bugs were found by reading logs. An alarm or a safety switch that has never fired is untested, so I triggered each one on purpose on the real deployment: a broken message for the dead-letter queue, a test alert for the cost guard, and a request flood for the request alarm.
  • Cost. Almost everything here costs nothing while idle, but a limit is only real once I know exactly what it counts. A throttle per method, a queue that is polled all day and a preflight request that anyone can send were all things I had to learn by working out what would actually be billed.

11. Results

The service is deployed and verified. On 5 November 2026 one terraform apply created 120 resources in us-east-2, and I verified the running service through the public page and its API the same day:

  • Sign-in through the Cognito hosted page, then upload, processing and download: three images were resized and downloadable 4.2 seconds after the click.
  • Ten images in one job finished in 6.7 seconds; the worker needed 5.7 seconds and 135 MB of its 1,024 MB.
  • Three jobs submitted together all completed on the first attempt, with the worker's concurrency peaking at 2, the cap I configured.
  • A corrupt file failed on its own with a clear reason while the other file in the job completed, and nothing was retried.
  • Two duplicate copies of a finished job's message were skipped; the job record and its outputs did not change.
  • Requests without a valid sign-in were refused, one account could not read another account's job or use its uploads, and the daily quotas refused the 11th job and the 21st upload request of the day.
  • An upload link used after its 60-second lifetime was refused by S3.
  • Both safety drills worked: a test alert paused the service within about a second, and a request flood tripped the alarm and paused the service automatically. The manual switch paused and restored the whole service with one command each.
  • A deliberately broken message was received three times, twelve minutes apart, then moved to the dead-letter queue, and the alarm fired three minutes later. The message was still there, intact, the next day.
  • Across the run there were zero Lambda errors and zero 5xx responses, and the logs contained no tokens, signatures or e-mail addresses.

The first deployment. On 4 November 2026 I deployed the queue-and-worker core on its own to test it before building the rest: 51 resources created, 59 jobs completed, a dead-letter drill in which a broken message was received three times, moved to the dead-letter queue and raised the alarm, two real bugs found and fixed from logs, and all 51 resources destroyed afterwards with nothing left behind.

Tests. More than 340 Python tests, 77 JavaScript tests, headless-browser tests of the console, Terraform formatting and validation, and a scan for secrets run on every push.

Cost. The deployment, every test and both drills together used about one cent of credit, read from the account's credit balance the next day, and the service costs close to nothing while idle. The project runs on AWS Free plan credits inside a $10 ceiling that I set for myself, with alerts and an automatic pause well below it.

12. What I would improve

  • Push instead of polling. The page asks for the job status every few seconds. A WebSocket API would push updates, at the cost of a connection table and more moving parts.
  • A per-user monthly quota and self-service sign-up. Today I create accounts by hand and limit jobs per day. Opening sign-up safely would need stronger abuse controls than I can run inside this budget.
  • A deployment pipeline. I apply Terraform by hand after reviewing the plan. A pipeline with a manual approval step would be more repeatable, but it needs AWS credentials in CI, which I chose not to do for a personal account.
  • Larger files. Files over 5 MB would need multipart uploads and more worker memory, which raises the cost per job.
  • A custom domain and CDN for the site. The console is a static site on GitHub Pages. S3 with CloudFront would keep everything on AWS; it adds resources to manage for no functional gain today.
