CloudFlow: engineering notes

CloudFlow is my serverless image-processing project on AWS. These notes record the decisions behind it, how failures are handled, how access and cost are controlled, and what was verified on the real services. The case study tells the story; this page is the reference.

Status. The service is deployed in AWS us-east-2 (120 resources from one terraform apply on 5 November 2026) and was verified end to end the same day. Live processing is limited to accounts I create, with daily quotas. Visitors without an account can use the browser demo, which resizes images in your browser and uploads nothing.

Architecture

browser ── POST /uploads ──▶ API Gateway ──▶ api Lambda ──▶ presigned POST forms
browser ── image bytes ───────────────────────────────────▶ S3 input bucket (private)
browser ── POST /jobs ────▶ API Gateway ──▶ api Lambda ──▶ DynamoDB (job queued) + SQS message (ids and keys only)
                                                              SQS ──▶ worker Lambda (Pillow) ──▶ S3 results bucket (private)
                                                                          └── claim, progress, outcome ──▶ DynamoDB
browser ── GET /jobs/{id} ─▶ API Gateway ──▶ api Lambda ──▶ status + presigned download links
                                                              SQS ── 3 failed receives ──▶ dead-letter queue ──▶ CloudWatch alarm ──▶ SNS

Why each service is there: API Gateway is the only public entry point (validation, throttling, authorization); Cognito identifies users without putting AWS credentials in the browser; SQS separates accepting a job from doing it; Lambda runs the API handler and the worker with no servers to keep alive; DynamoDB holds job state and makes "claim this job" a single atomic write; S3 stores inputs and outputs privately; IAM limits each function to the exact actions and resources its code uses; CloudWatch, SNS and X-Ray turn silent failures into signals; Terraform creates and destroys all of it from one reviewed plan.

The Architecture page of the console draws this as an interactive diagram. It is generated from one data file whose configuration facts each carry a pattern that must match the Terraform they describe; an automated test fails if a memory size, timeout, retention period, IAM statement or alarm drifts from the diagram, or the other way round. Request, data, status, identity and failure paths have distinct line styles; image bytes are never drawn through SQS, because messages carry only keys; and IAM, X-Ray, CloudWatch Logs, AWS Budgets and Terraform sit in a separate strip with no arrows, because they govern the services and do not carry traffic.

Decisions

Why a queue instead of doing the work in the request. API Gateway cuts a request off at 29 seconds, and a burst of uploads would overload a synchronous worker. Accepting the job in milliseconds and processing it from a queue keeps the API fast, lets the worker scale on its own, and gives every failure a retry path. The cost is that the client has to ask for the result; the page polls a status route.

Why uploads skip the API. Image bytes sent through API Gateway and Lambda would be slow and would hit payload limits. The API returns a presigned POST form instead, and the browser sends the file straight to S3. My code still decides exactly what is allowed: the form pins one key under the user's own prefix, one content type and a size range of 1 byte to 5 MB, and it expires after 60 seconds.

How the worker scales and processes jobs. An event source mapping polls the queue and invokes the worker with one message at a time, with at most two workers running at once. The worker reports which records failed (ReportBatchItemFailures), so a bad message is retried on its own. In the live run three jobs submitted together all completed on the first attempt and concurrency peaked at exactly 2.

How DynamoDB handles state and concurrency. One item per job. SQS delivers at least once, so two copies of a message can be processed at the same moment. A job is claimed with a single UpdateItem whose condition allows the write only if the job is new, queued, retryable, or held by a lease that has expired. The worker records a lease; every later write is conditional on still holding it, so a worker that outlived its lease cannot overwrite a newer outcome. A refused claim returns the current item in the same call, so the worker can tell a finished job from one that another worker is still processing. A duplicate that finds a live lease is put back for later, never deleted, because deleting it could remove the only remaining copy. In the live run, two extra copies of a finished job's message were skipped and the record and outputs did not change.

How IAM is restricted. Five roles, one per function plus one for the legacy queue integration, each with the exact actions its code calls on named resources. The API function can create upload forms, read and write job items, query one index and send to one queue; it cannot list a bucket, delete an object or scan the table. The worker can read under uploads/ and write under results/ and nothing else in S3. The cost guard can write one single item and change one API stage. The only * resource is X-Ray, which supports nothing narrower. A test parses the Terraform on every push and fails if a statement widens, if a role gains a policy outside the reviewed set, or if a managed policy appears.

What happens on failure. Three kinds, decided per message. A broken message (no usable job id) is reported, nothing is written, and after three receives SQS moves it to the dead-letter queue, where an alarm watches. Bad input (invalid options, a corrupt or oversized image) is recorded as failed and never retried, because retrying cannot fix it; a corrupt file fails on its own while the other files in the job finish. A temporary AWS error is recorded with a short error code and the message is retried after the visibility timeout.

What is logged and monitored. Each function has its own log group with 14-day retention. Log lines carry ids, decisions and error codes, never payloads, tokens or raw exception text; error bodies returned to clients are fixed strings. A pattern search over every log line from the live run found no token, signature, key or e-mail address. Seven alarms: dead-letter queue depth, errors in the worker, the API function and the cost guard, and the API request count over 5 minutes, an hour and a day.

How cost is controlled. Everything is pay-per-request; nothing is billed by the hour. Sign-in is required and accounts are created by me. Daily quotas limit jobs (10 per account, 30 for the whole service) and upload requests (20 per account, 60 in total); both counters are updated in one DynamoDB transaction. API Gateway throttles each method separately at 1 or 2 requests a second. An AWS Budget measured on usage before credits alerts at 20, 50, 80 and 95 percent of $10. The 80 and 95 percent alerts and the three request-count alarms invoke a small guard function that turns processing off and sets every throttle to zero; an operator script does the same by hand. AWS has no hard spending cap below the Free plan itself, so I describe this as alerts plus a fail-closed switch, not a guarantee. One risk is accepted and written down: whoever holds a presigned upload form can repeat that upload until it expires, which is why accounts are by invitation.

How Terraform provisions and destroys. One configuration, one plan reviewed before any apply, one destroy with both buckets set to empty themselves. State and variables are git-ignored. The configuration validates without the Pillow layer archive and refuses to plan without it; preconditions fail the plan if a request schema's limits drift from the variables.

Tests

More than 340 Python tests (pytest with an in-memory AWS emulator and real sample images), 77 JavaScript tests for the console, and headless-Chrome checks that drive the published page, including the browser demo with real files. Terraform formatting and validation and a secret scan run with them in GitHub Actions on every push. CI never touches the AWS account.

Two problems I found on AWS and fixed

Both came from my first deployment, on 4 November 2026, when I deployed only the queue-and-worker core to test it before building the rest.

  1. Every submission returned 500. The role that API Gateway uses to write to the queue had an aws:SourceAccount condition in its trust policy. API Gateway does not supply that value when it assumes a role for a service integration, so the role could never be assumed. I found it in the execution log and removed the condition from that one role; the Lambda roles keep it.
  2. Download links answered 403. Links were being signed for the general S3 address. S3 redirected the request to the bucket's regional address, and because the signature covers the host name, the redirected request failed. I fixed it by signing against the regional endpoint and added a test for the host name in the link.

Both were diagnosed from logs, fixed, redeployed and re-verified within the hour.

Limitations

  • The service runs on an AWS Free plan account and cannot outlive that plan; if the backend is paused or gone, the site keeps working as a browser demo.
  • Live access is by invitation, for the cost reason above.
  • The page polls for job status every few seconds; a WebSocket API would push updates instead.
  • Files are limited to 5 MB and 24 megapixels; larger files would need multipart uploads and more worker memory.
  • The browser demo mirrors the worker's limits and geometry but is not the same code. Known differences: browser encoders produce different file sizes from Pillow at the same settings, browser PNGs are always RGBA, WebP encoding depends on the browser, the browser applies an embedded colour profile while decoding where Pillow drops it, and an image over 24 megapixels is reported as "too large" in the browser but as "unsupported or corrupt" by the worker.
  • Single region, no custom domain, no WAF: deliberate for a small personal project.
