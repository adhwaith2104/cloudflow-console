Presigned URL 403 (sanitized)

Symptom in pass 2: GET /status/{jobId} returned a resultUrl, but urllib following it got HTTP Error 403: Forbidden after a redirect.

Cause: the status function presigned with boto3's default S3 client, which produced the legacy global host bucket.s3.amazonaws.com. For a bucket in us-east-2, S3 answers that host with a redirect to bucket.s3.us-east-2.amazonaws.com. The signature covers the host header, so the redirected request no longer matches and S3 returns 403.

Fix in app/status.py: build the S3 client with region_name, endpoint_url = https://s3.<region>.amazonaws.com, and Config(signature_version="s3v4", s3={"addressing_style": "virtual"}). Regression test asserts the regional host in the URL.

Verified live in pass 3: host ...s3.us-east-2.amazonaws.com, credential scope us-east-2/s3/aws4_request, X-Amz-Expires=300 (expiry = X-Amz-Date + 300 s), HTTPS GET → 200 with 0 redirects, downloaded JSON byte-identical to the object read through the S3 API (sha256 equal), tampered signature → 403.

The next day the message was still in the dead-letter queue with its body intact and a receive count of 4 (three by the worker, one by the operator reading it). It was read and deleted with operator credentials at 17:25 on 2026-11-06, and the alarm returned to OK. No job item was written for it, and processor-errors stayed OK throughout, because the worker reports a bad message and does not crash on it.

One thing the overnight history showed: the alarm briefly changed to OK and back to ALARM about seven hours after the message arrived (03:19 to 03:21 UTC). The queue had seen no activity for more than six hours, and SQS stops publishing metrics for idle queues, which the alarm treats as "not breaching" until the next datapoint. The message was never lost; a real operator would see the first ALARM notification.

The alarm e-mail itself was not observed: the SNS e-mail subscription had not been confirmed.

9. Kill-switch drill and the day after (2026-11-06)

Operator kill switch (17:25:39). kill_switch.py disable --yes wrote the control item (enabled = false, reason operator kill switch), disabled the queue-to-worker mapping and set the default and all nine method throttles to zero; exit code 0. Preflight requests answered 200 for about 25 seconds while API Gateway applied the change, then 429. kill_switch.py enable --yes (all three request alarms were OK, so it did not refuse) restored the switch, the mapping and every throttle; the first 200 came about 17 seconds later, and status showed the mapping Enabled and the planned values.

Cleanup. The two temporary verification accounts were deleted and their passwords removed from the operator's machine; the user pool holds no users until the owner creates their own.
